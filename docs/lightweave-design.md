# 《织光》· 微信小游戏设计方案

> 类别：**益智（连线解谜）**
> 一句话：**从一端拖到另一端，用彩色的线把整块夜园点亮。**
> 文档状态：待评审 · 目标首版 144 关 + 每日一图

---

## 1. 为什么选「益智」

在动手前先按微信小游戏的现实约束给五个类别打分（5 分制，分越高越好）：

| 维度 | 消除 | 答题 | 模拟经营 | 塔防 | **益智** |
| --- | --- | --- | --- | --- | --- |
| 美术成本（越低分越高） | 2 | 4 | 1 | 1 | **5** |
| 内容/合规成本（越低分越高） | 3 | 2 | 3 | 3 | **5** |
| 与现有零资源 Canvas 管线契合 | 3 | 3 | 1 | 1 | **5** |
| 首屏 10 秒可玩性 | 5 | 4 | 2 | 2 | **5** |
| 微信生态（分享/排行/每日） | 4 | 5 | 4 | 3 | **4** |
| 竞争激烈程度（越低分越高） | 1 | 1 | 2 | 2 | **4** |
| **合计** | 18 | 19 | 13 | 12 | **28** |

逐条说明：

- **消除**：红海。仓库根目录已经有一款《贝壳消消乐》，再做一遍既重复又要补大量美术与关卡，性价比最低。
- **答题**：技术上最省（几乎无美术），但**内容成本与合规风险最高**——题库版权、答案争议、以及"答题赢奖励"类玩法在审核上容易被额外关注。不适合作为第一个自研小游戏。
- **模拟经营 / 塔防**：都需要成体系的美术资产和大量 UI，Canvas 手写 UI 的边际成本很高；且两者都是重数值、长会话，与微信小游戏"点开即玩"的节奏相反。
- **益智**：唯一同时满足「零资产可做」「内容可程序生成」「十秒上手」的类别，而且能 100% 复用现有管线（`Host` 契约、音频总线、构建工具链、无头测试）。

**结论：做益智，具体子类做「连线解谜」（Flow / Numberlink 类型）。**

连线在触摸屏上的操作是**拖**，比点击/旋转更直觉，不需要教程；完成判据是"整块棋盘被填满"，视觉上极其明确，天然有"再来一关"的冲动。

## 2. 体验目标

打开 → 看见一块暗着的花园格子 → 手指从一个光点拖到另一个光点 → 一条发光的藤蔓长出来 → 最后一对连上时整块视野亮起。

三条原则：

1. **零教程**：第一关只有 3 对点、5×5 格，玩家瞎拖也能过，过关时自动理解规则。
2. **零失败**：没有步数限制、没有倒计时、没有体力。只有"完美"和"不完美"。
3. **随时断**：单关 40–90 秒，切后台不丢进度，回来接着拖。

## 3. 核心玩法

### 3.1 规则

- 棋盘是 `W × H` 的格子，上面有 `N` 对**同色端点**（2–7 对）。
- 从任意端点按住拖动，画出一条线，连到同色的另一个端点即连通。
- **线不能交叉**、不能穿过别人的线、不能穿过障碍格。
- 拖动时可以**回退**：手指退回上一格，线就缩短一格。
- 再次按住一条已存在的线，可以从任意位置继续编辑（拆掉后半段）。
- **通关条件**：所有颜色都连通。
- **完美条件**：所有格子被线填满。

```
未完成                          完美过关
┌─┬─┬─┬─┬─┐                    ┌─┬─┬─┬─┬─┐
│●│ │ │ │ │                    │●━━━━━━━━●│
├─┼─┼─┼─┼─┤                    ├─┼─┼─┼─┼─┤
│ │ │●│ │ │                    │ ┃ │●━━━━●│
├─┼─┼─┼─┼─┤                    ├─┼─┼─┼─┼─┤
│ │ │ │ │ │                    │ ┃ │ ┃ ┃ │
└─┴─┴─┴─┴─┘                    └─┴─┴─┴─┴─┘
```

### 3.2 操作细节（手感关键）

| 行为 | 反馈 |
| --- | --- |
| 按住端点 | 端点放大、呼吸光圈、轻震动（light） |
| 拖入新格子 | 格子亮起、线头带拖尾粒子、每 3 格升半音（音阶随颜色变） |
| 拖不动（撞线/撞墙/单向逆行） | 线头抖一下、闷响、不振动 |
| 连成一对 | 整条线闪一下、清脆音、端点从"点"变成"结" |
| 全部连通 | 屏幕轻微泛白、障碍石碎裂、每对线依次点亮（0.12s 间隔） |
| 全格填满 | 额外的"完美"涟漪 + 星屑喷发 |

移动端要点：手指会挡住目标格，所以**线头始终画在手指上方 24px**，并给一个半透明的手指偏移指示。

### 3.3 星级

| 星级 | 条件 |
| --- | --- |
| ★★★ | 全部连通 **且** 全格填满 **且** 未使用提示 |
| ★★ | 全部连通 **且** 未使用提示 |
| ★ | 全部连通（用过提示） |

三星的设计意图：把"过关"和"完美"分开，让手残玩家也能推进，让硬核玩家有追求。

## 4. 关卡系统

### 4.1 特殊格子（按章节逐个引入）

| 章节 | 新机制 | 说明 |
| --- | --- | --- |
| 1 夜园 | — | 纯基础，5×7，4 色 |
| 2 石径 | **障碍格** | 不可通过，用来收窄解法 |
| 3 风径 | **单向格** | 只能按箭头方向穿过 |
| 4 泉眼 | **传送门** | 成对出现，进入即从另一端出来 |
| 5 棱镜 | **变色格** | 穿过时线变成另一种颜色（用于制造"借道"） |
| 6 星穹 | 混合 | 7×10 大棋盘，多机制叠加 |

每章 24 关，首版共 **144 关**。第 1 关强制"随便拖都能过"，第 2–4 关逐步把机制喂给玩家。

### 4.2 关卡生成（保证有解）

连线类关卡不需要手摆，用**"先造解、再挖洞"**的方式生成：

```
1. 用随机 DFS 把 W×H 棋盘切成 K 条互不重叠的蛇形路径（覆盖所有格子）
   - 每条路径长度限制在 [4, 14]
   - K = 颜色数
2. 每条路径的两个端点在棋盘上的格子 → 成为一对同色端点
   → 此时"全格填满"的完美解必然存在
3. 可选：删掉部分路径中段的格子，变成障碍格（保持剩余路径连通）
4. 根据第 2 步得到的真实走向，给部分格子标上单向箭头（一定与解一致）
5. 计算 par：完美解所需的"最少拆线次数"，用于三星阈值和提示
```

- 失败重试：若某条路径长度 < 4 或某颜色端点相邻（太简单），整盘重来，最多 200 次。
- 难度参数：`棋盘面积 / 颜色数 / 障碍数 / 单向数 / 最短路径长度`。
- 生成器同时输出 `solution`，只用于**提示**与**内部校验**，不进客户端。

### 4.3 数值曲线

| 章节 | 棋盘 | 颜色数 | 特殊格 | 目标通关时长 |
| --- | --- | --- | --- | --- |
| 1 | 5×7 | 4 | 0 | 30–45 s |
| 2 | 5×8 | 4–5 | 1–3 障碍 | 40–60 s |
| 3 | 6×8 | 5 | 2–4 单向 | 50–75 s |
| 4 | 6×9 | 5–6 | 2 传送 | 60–85 s |
| 5 | 6×9 | 6 | 2–3 变色 | 65–90 s |
| 6 | 7×10 | 6–7 | 混合 | 75–120 s |

### 4.4 每日一图

- 以日期为种子（`seed = dayIndex`），全场同一张图，一天一次。
- 记录"当日最快通关时间"与"是否完美"。
- 连续完成 7 天解锁限定主题「极夜」。
- 断签不清零累计天数，只清连续数——不惩罚玩家。

| 通关 | 10 |

> 所有来源与消耗都是确定数值。见 §11。

### 5.2 主题（内容的第二增长点）

换的不只是配色，还包括：背景氛围、线材质（藤蔓 / 水流 / 星轨）、音阶。

| 主题 | 获取 |
| --- | --- |
| 夜园（默认） | 初始 |
| 深海 | 200 星屑 |
| 竹林 | 400 星屑 |
| 雪原 | 800 星屑 |
| 极夜 | 连续 7 天每日一图 |

### 5.3 进度与回流

- 首页即"星图"：每章一块星区，点亮的关卡越多星区越亮。
- 每日一图 + 连续天数。
- 章节解锁用星星总数（与"必须全三星"解耦，避免卡死）。

## 6. 微信生态与变现

| 能力 | 用法 | 注意 |
| --- | --- | --- |
| 转发卡片 | 过关后"把这一关发给好友" | 用 `wx.canvasToTempFilePath` 生成 5:4 分享图；**不绑定任何奖励**，不做强制分享 |
| 开放数据域 | 好友本周通关数排行 | 需单独的 `openDataContext` 目录 + `game.json` 配置；只展示好友，数据不出平台 |
| 激励视频 | 补 1 次提示 / 双倍星屑 | `wx.createRewardedVideoAd`；有明确"广告"标识与跳过入口 |
| 插屏 | 每 5 关一次，冷却 ≥ 90 s | 不在拖拽过程中弹，不遮挡棋盘 |
| 本地存储 | 进度 / 货币 / 主题 | 单 key ≤ 1 MB，总 ≤ 10 MB；不含任何个人信息 |

**合规模块**（提审前必须完成，详见 §11）：小游戏类目选「休闲益智」、版号/备案、软著、实名与防沉迷、
适龄提示、隐私政策与用户协议。这些与代码解耦，但会卡上线时间。

## 7. 技术方案

### 7.1 复用现有架构

上一次已经把"平台无关玩法"抽出来了，这次继续沿用同一套分层：

```
shared/
├── engine/              ← 新增：从 squishy-planet 抽出的公共层
│   ├── platform/        Host 契约 + 浏览器 Host
│   ├── audio/           InnerAudioBus / WebAudio
│   ├── core/            数学 / 颜色 / 绘制 / 设计坐标
│   └── tools/           PNG、WAV、图标、无头测试 harness
├── squishy-planet/      ← 已有，改为依赖 engine（仅移动文件 + 改 import）
└── lightweave/          ← 新增：《织光》的全部玩法
    ├── src/game/        棋盘、路径、生成器运行时校验、渲染、HUD
    └── src/index.ts     对外只暴露 startLightweave(host)
wx-lightweave/           ← 新增：平台工程，只放 wx 适配层与构建脚本
```

> 平台适配层已经在 `wx-mini-game/src/platform/wx.ts` 验证过，新工程直接复用即可，
> 真正要新写的只有"玩法"本身。

### 7.2 分层与渲染

| 层 | 内容 | 重绘时机 |
| --- | --- | --- |
| 背景 | 渐变 + 星点 + 缓慢漂移的雾 | 每帧（很便宜） |
| 棋盘 | 圆角格子、障碍石、单向箭头、传送门 | 变化时 |
| 路径 | 三次绘制的发光折线（粗 → 中 → 细） | 每帧（拖动时） |
| 端点 | 发光球 + 连成后的"结" | 每帧 |
| 拖拽头 | 跟随手指的线头 + 粒子 | 每帧 |
| HUD | 顶部关卡/星级、底部提示按钮 | 变化时 |

- 发光**不用 `shadowBlur`**（小游戏里很慢）：同一路径画 3 遍，`lineWidth` 递减、`alpha` 递增。
- 路径用「单元格中心的圆角折线」而不是贝塞尔，转弯处用 `arc` 过渡，保证拖拽时线条不抖。
- 棋盘最大 7×10 = 70 格，重绘成本可以忽略。

### 7.3 数据结构

关卡（客户端只读）：

```json
{
  "id": "3-07",
  "cols": 6,
  "rows": 8,
  "pairs": [
    { "color": 0, "a": [0, 2], "b": [5, 5] },
    { "color": 1, "a": [1, 0], "b": [4, 7] }
  ],
  "walls": [[2, 3], [3, 3]],
  "oneWays": [{ "x": 1, "y": 4, "dir": "right" }],
  "portals": [[[2, 5], [5, 1]]],
  "par": 46
}
```

存档：

```json
{
  "version": 1,
  "stars": { "1-01": 3, "1-02": 2 },
  "dust": 320,
  "theme": "night",
  "owned": ["night", "deepsea"],
  "daily": { "date": "2026-10-23", "best": 63, "perfect": true, "streak": 5 },
  "seenTutorial": true
}
```

### 7.4 输入与路径构建

```
pointerdown → 命中端点或已有线 → 选定颜色，记录路径
pointermove → 换算成格子坐标
             ├ 与上一格相邻且可进入 → 追加
             ├ 回到上一格         → 回退
             └ 其余               → 忽略（并给"撞墙"反馈）
pointerup   → 提交；全部连通则结算
```

要点：

- 手指按下与移动的采样频率在小游戏里约 30–60Hz，快速拖动会**跳格**；
  需要用 Bresenham 把上一格到当前格之间的格子补上，并在不可进入的格子处截断。
- 编辑既有路线时，从按下的那一格开始截断后半段，符合直觉。

### 7.5 性能

- 单帧：≤ 70 格 × 若干路径段 + 200 粒子，中端机稳 60fps。
- 拖动时只重绘「路径层 + 拖拽头」，棋盘层缓存到离屏 canvas。
- 包体预估：代码 60–80 KB + 音效 120 KB ≈ **200 KB**，远低于 4 MB 主包限制。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 生成器产出的关卡"没意思" | 核心体验崩塌 | M1 先手摆 12 关做基准；生成器必须能复现同一种手感，再批量产 |

| 审核被判定"简单拼图" | 驳回 | 强调原创美术与关卡生成，保留生成算法与设计文档备查 |

## 11. 内容合规自审

> 本节是**设计自检**，不是法务意见，也不替代平台审核与主管部门审批。
> 结论：本设计在题材、玩法、表现、变现、社交五个维度均未触及下列法规的禁止性内容。

### 11.1 法规对照

| 法规 | 主要禁止项 | 本设计的对应情况 |
| --- | --- | --- |
| 《出版管理条例》第二十五、二十六条 | 反对宪法确定的基本原则；危害国家统一、主权和领土完整；危害国家安全、荣誉和利益；煽动民族仇恨、民族歧视；破坏国家宗教政策，宣扬邪教和封建迷信；散布谣言、扰乱社会秩序；宣扬淫秽、色情、赌博、暴力、凶杀、恐怖或者教唆犯罪；侮辱诽谤他人 | **不涉及**：题材为抽象的"夜园—星穹"，无政治、民族、宗教、军事元素；无写实暴力、血腥、死亡表现；无赌博机制；无淫秽低俗；无对真实人物或事件的影射（详见 11.2） |
| 《互联网信息服务管理办法》第十五条 | 上述九类禁止内容 + 侵害他人合法权益 + 法律禁止的其他内容 | **不涉及**：同上；首版**不含任何用户生成内容（UGC）**，不存在第三方上传内容带来的审核盲区；不展示用户昵称/签名 |
| 《网络出版服务管理规定》第二十四、二十五条 | 网络出版物不得含有禁止内容；须依法取得网络出版服务资质并建立内容审核制度 | **设计层不涉及**禁止内容；**运营层**需按当期政策办理版号/备案与内容自审制度（见 11.3） |
| 《移动游戏内容规范》 | 赌博与概率玩法、色情低俗、暴力恐怖、封建迷信、涉政涉军涉恐、诱导消费、诱导分享、未实名/未防沉迷、缺少适龄提示、隐私违规 | **逐条对应**，见 11.2 的红线承诺 |

### 11.2 设计层面的红线承诺（写入需求，实现时不得突破）

1. **无概率玩法**：没有抽卡、转盘、盲盒、开箱、扭蛋。星屑的全部来源与消耗都是确定数值。
2. **无付费货币**：星屑不可充值、不可提现、不可兑换任何现实权益；首版**不设内购**。
3. **无暴力**：无战斗、无角色受伤或死亡；"障碍石碎裂"只是几何图形的破碎动画，无写实破坏与不可控伤害表现。
4. **无恐怖与迷信**：无惊悚元素、无尸体/血迹、无宗教符号与仪式、无占卜算命。"星图"仅指进度地图，"星屑/夜园"是纯粹的美术命名。
5. **无 UGC**：首版不做自定义关卡、不做昵称/签名/留言展示，从源头避免 UGC 审核义务。
6. **广告合规**：只用平台激励视频与插屏；有明确广告标识与关闭入口；不在拖拽操作中弹出；不遮挡核心玩法；不对未成年人做定向诱导。
7. **分享合规**：分享**不绑定任何奖励**，不做"分享才能继续""分享得星屑"；不强制、不反复骚扰。
8. **个人信息最小化**：进度、货币、星级全部存本机 `wx.setStorageSync`；不上传服务器；排行榜通过微信开放数据域，数据不出平台；不采集手机号、位置、通讯录等。
9. **适龄提示**：启动页与设置页展示适龄提示图标（建议 **8+**）与健康游戏忠告；不使用会引发不适的视觉刺激。
10. **未成年人保护**：接入平台实名与防沉迷能力；未成年人按平台规则限制游戏时长与广告展示；无内购，因此不存在充值限额问题。

### 11.4 后续版本的合规前置条件

如果 1.1 上线**关卡编辑器**，游戏将从"无 UGC"变为"含 UGC"，需要同步补齐：

- 文本/图形式内容的过滤与敏感词库；
- 用户举报入口与处置流程；
- 关卡审核（先审后发或先发后审 + 巡查）；
- 未成年人保护与侵权投诉通道。

在这些能力就绪之前，编辑器不进入线上版本。

### 11.5 自审结论

| 维度 | 判定 |
| --- | --- |
| 题材 | 抽象奇幻，无政治/民族/宗教/军事敏感 |
| 玩法 | 连线解谜，无赌博、无概率、无暴力、无恐怖 |
| 表现 | 几何图形与光效，无色情低俗、无血腥 |
| 变现 | 无内购；仅激励视频与插屏，符合广告规范 |
| 社交 | 仅平台内分享与好友排行，不绑定奖励、不采集个人信息 |
| 结论 | **未发现违反上述法规的内容**；最终过审取决于资质材料与平台当期审核口径 |

### 12.2 与设计的偏差（都是有意为之）

| 项 | 设计 | 实现 | 原因 |
